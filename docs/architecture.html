Partner Radar, end to end

A tool for legal recruiters. It crawls the public websites of 15 target law firms, tracks every Corporate & M&A partner, detects joins, departures, lateral moves and promotions, and writes cited call‑prep briefs on demand. Crawling, parsing and change detection are deterministic. The LLM is used last: it turns stored facts into prose, and it tags practice labels that no keyword rule recognises.

Underneath, it is a general tracker of people at organisations. Corporate & M&A partners at law firms are one domain profile. A second profile, footballers at clubs, ships to show that retargeting the tool is a configuration change.

SHEET 1

System architecture

One docker compose stack with four services. api and worker are the same Python package (backend/src/radar) started with two entrypoints. MongoDB stores the data, what to track (organisations and the domain profile), and the job queue. The CLI (make …) calls the same functions.

SHEET 2

What we track is configuration

Two things decide what the radar collects: the organisations to crawl and the domain profile that says who counts and what they're called. Both follow the same pattern. A YAML file seeds a MongoDB collection on startup, admins edit the collection in the UI, and an edited entry (managed: true) is never overwritten by the YAML again. The worker reloads both every scheduler tick, so changes apply within a minute without a restart.

The domain profile holds the vocabulary (Partner/Firm/Practice, or Player/Club/Position), the canonical titles and which ones count as a promotion, the group taxonomy with its keyword rules, segments (which organisations × titles × groups get full profiles), extra fields such as bar admissions, the seniority rule, and the context the AI writes for. Run one domain per deployment.

SHEET 3

The crawl pipeline

The worker runs this sequence for every enabled organisation. Each step is a job in the Mongo queue, claimed atomically with a lease. Parallelism happens across organisations, never within one site. Orchestration lives in radar/worker/crawler.py.

  1. Discover

    scraping/sources.py · sitemap.py

    Daily per organisation. Two source types: an XML sitemap, or an HTML listing page with a link selector and an optional "next page" selector. Either way the result is a list of profile URLs. New URLs, a changed <lastmod>, and stale profiles (7 days in segment, 30 days otherwise) are queued.

  2. Fetch

    scraping/fetcher.py · raw_store.py

    One polite client: robots.txt cached daily, ≥3 s per site, conditional GETs, Retry-After. A 403 or 429 marks the organisation blocked for 24 h. When a profile changed, the raw page is kept for people in a segment only; anyone else keeps just the minimal record in their observation.

  3. Extract

    scraping/extract.py

    A cascade: configured CSS selectors, then JSON‑LD Person, then heading heuristics, then <h1>. The profile's extra fields are found by heading or schema.org property. Each field records which method produced it.

  4. Normalise

    pipeline/normalise.py · llm/classify.py

    Titles map to the profile's canonical titles. Group labels are tagged by the taxonomy's keyword rules first. A label no rule matches is sent to the LLM once, and the answer is saved in label_tags. Education gives seniority_year. A missing value never overwrites a known one.

  5. Diff → events

    pipeline/diff.py

    Hash of the extracted record. If unchanged, stop. Otherwise emit joined, promoted (into a promotion_to title), title/office/group_changed, and left only after two sitemap misses plus a 404/410.

  6. Match moves

    pipeline/matching.py

    A departure at organisation A and an arrival at B within 120 days, scored on name, school, seniority year and group overlap. Name alone gives a "possible move" for a human to confirm.

  7. Lift‑outs & signals

    worker/crawler.py · signals.py

    Two or more departures from one office within 60 days raise lift_out. Signals such as "organisation net flow −3" are derived from history, without AI.

Safeguards against false departures

  • If the sitemap shrinks by more than 15%, the run is quarantined: new profiles are still processed, but nobody is marked as departed.
  • Zero profiles found means the run is broken. It does not reset the baseline.
  • Saved label tags mean a re-crawl always tags a label the same way, so the AI can't invent a "groups changed" event.
  • Per-field fill rates on the Organisations page give early warning that a site's layout changed (pipeline/health.py).
  • make reprocess or Reprocess everyone re-parses stored raw pages after a fix or a profile edit, with no network requests to the sites. Out-of-segment people are re-classified from their stored record instead; if that puts someone in a segment, their profile is fetched again for the full details.
  • Once a day the worker purges raw pages: out-of-segment people's pages are unlinked, and any page no observation refers to is deleted after a day (purge_raw in worker/crawler.py).
SHEET 4

The AI path: one choke point

Every LLM feature goes through LlmGateway.run. A feature supplies a task name, a prompt version and an output schema. The gateway handles everything else, so no feature can bypass cost control.

TaskDefaultWhen it runsWhat goes to the model
call_prep_briefOnA recruiter asks for a brief on a person page; cached by input hashNumbered facts about one person from MongoDB (llm/prompts/brief.md)
classify_labelOnDuring normalise, for a group label no keyword rule matches; once per distinct label and taxonomy versionThe label text and the category list only, no personal data (llm/classify.py)
org_setupOnAn admin adds an organisation and asks the AI to fill in its scraper settings; every suggestion is validated, then surveyed before savingThe name typed, or a summary of the site's structure: sitemaps, links, a sample profile skeleton (llm/onboard.py)
market_digestOffAn admin or recruiter asks for the weekly summary of movesThat period's events
SHEET 5

Data model (MongoDB)

Indexes are created at startup in radar/db.py and the document shapes live in radar/models.py. A person is read as a single document, so their history and per-field provenance are embedded in it.

SHEET 6

Frontend pages and the API they call

The routes are in frontend/src/App.tsx; page and menu labels come from the domain profile's vocabulary. Client types are generated from FastAPI's OpenAPI schema (frontend/openapi.json → src/api/schema.d.ts), so the backend and frontend cannot drift apart without a type error.
